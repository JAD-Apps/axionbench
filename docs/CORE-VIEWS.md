# Rankings, benchmarks and domains

Rankings offer bars, dots and a table. The default uses primary-confirmed model identities and maintained exact benchmark/harness versions. This snapshot has four eligible BFCL configurations for two models. The historical selector retains the qualified older panels; their wider coverage is labelled historical. Selecting one source/suite/metric panel never merges its configurations with another version. Representatives use each model’s highest listed configuration on that panel, with every configuration still selectable. This is not a common-setting aggregate.

The benchmark page has two separate datasets. BridgeBench offers bars, dots and a table for each of its ten native rating axes. Its overall rating includes cost and speed. Those ratings are publisher comparisons with an unpublished protocol, sample size and uncertainty; they never enter the accuracy index. You can include all published identities or restrict to primary-confirmed identities. For example, a native rating of 646 stays 646 BridgeBench rating units. The captured model-card section offers the same views for raw source claims, with visible verification and unit status. A mixed or unknown unit prevents a shared numerical axis; exact claims stay available in text.

Domains offer a heatmap, radar and table for the selected pair and weights. Each domain uses the existing strict current-policy/common-panel/family-cap calculation. A family with several suites counts once before the domain mean is calculated. A partial domain view does not make the incomplete overall index available. The current pair has one comparable domain, tool use: the two BFCL condition means are `(0.7747 + 0.3347) / 2 = 0.5547` and `(0.687 + 0.2526) / 2 = 0.4698`. Other domains are missing, so the equal eleven-domain index stays unavailable.

Every domain plot uses normalized fractions from 0 to 1, labelled 0–100%. Radar datasets contain actual nulls for missing or zero-weight spokes, use `spanGaps: false` and `fill: false`, and disclose the comparable spoke count. The current radar contains two points on one shared spoke, not complete polygons. Do not interpret a zero-weight gap as a failed test. Changing weights, using covered domains, resetting, sharing and exporting preserve the original common-panel rules. Weight perturbations, omitted-suite runs and the independent-only check remain sensitivity scenarios, not confidence intervals.

Canvas, keyboard inspection, tooltips, tables and JSON downloads consume the same `ViewRow` projection in `src/charts/rows.ts`. It retains stable observation/model IDs, plot and native values, units, exact suite or snapshot versions, missing reasons, source class, coverage and original links. Authority plots use the source-documented normalized fraction but text and exports retain its original fraction or percentage. Source intervals remain whiskers only where published. Hover a mark, or Tab to an inspection row and press Enter/Space, to read the same contextual tooltip and follow the result link. Each graphical view has an expandable accessible table; table view makes it directly visible. Scrollable tables and the wide heatmap are keyboard focusable.

## Chart implementation

Chart.js is pinned to 4.5.1 with the existing exact npm package manager and lockfile. `src/charts/registry.ts` explicitly registers bar, scatter and radar controllers, their elements, and category/linear/radial scales. `CoreChart` owns one instance, updates it in place for changed values and sorts, and stops/destroys it on view changes and unmount. Stable observation IDs carry existing elements through a reorder; radar dataset objects are retained by model identity. Motion animates the position of keyed inspection rows. Chart transitions last 380 ms. A shared media-query subscription responds to runtime preference changes. Reduced motion stops Chart.js animation, disable Motion layout transitions, and remove tooltip/control CSS transitions without changing values.

The original heatmap uses the registered scatter controller and `src/charts/heatmap.ts`, a local `afterDatasetsDraw` plugin. Scatter x/y values are categorical domain/model positions, never scores. The plugin draws rounded cells from each row’s normalized value, on a fixed cyan intensity scale; null cells use hatching and a dash. Chart.js supplies scale positions, resizing and point hit testing. No matrix dependency or stock appearance is used. This follows the [Chart.js plugin interface](https://www.chartjs.org/docs/latest/developers/plugins.html). Lifecycle cleanup follows [Chart.js destroy](https://www.chartjs.org/docs/latest/api/classes/Chart.html#destroy).

The replaced authority/benchmark visx components are removed. Remaining visx imports belong to task pricing, open weights and regional views, which are replaced in later phases. Motion remains for the hero/page and useful row transitions. The initial homepage JavaScript remains separate from the detailed comparison chunk.

## Share links and checks

View state is dataset-specific: `rankingView`, `bridgeView`, captured `view`, and `domainView`. Rankings retain `authority`, `authorityPolicy`, `authorityVersion`, `authorityCohort` and `authorityConfig`. BridgeBench retains `bridgeAxis`, `bridgeCohort`, `bridgeVersion` and `bridgeSelected`. Captured claims retain `suite`, `suiteVersion`, `cohort`, `domain`, `lab` and `selected`. Domains retain `w`, `weight-models`, `domainCell`, exact `domainSuites` and `domainSnapshot`. Version/snapshot keys describe the currently displayed projection; a refresh can change the available current data. Discrete view/filter changes create history entries, and hard reload or Back/Forward restores the saved controls. Copy the page URL or use Share weights to share it.

Run `npm run test:core-views` after installing with `npm ci`. It builds production output, then tests each selectable view at 390, 768 and 1440 px in installed Chromium, with `CHROMIUM_PATH` as an override. Evidence stays in ignored `test-results/core-views/`: source/data/build hashes, screenshots, downloads and a report. Canvas diagnostics record actual Chart.js geometry and registry counts so the browser gate compares rendered coordinates and lifecycle state with independent source values and hand calculations. Tests include native-unit parity, unknowns, sparse radar skips, keyboard/touch, source navigation, history/reload, exports, default/custom distinction, sensitivity, normal animation and live reduced-motion changes. `tests/core-views.test.ts` checks zero versus missing values, family caps, incompatible conditions, ineligible versions and duplicate rows.

The public allowlist includes these sources, documentation and checks. Public verification runs the same gate from the portable public tree and retains its evidence. The private release verifier adds this gate while keeping every existing data, source, math, pricing and release gate. Passing local checks is not deployment or independent-review evidence.

Portable preparation relocates only the product route/core browser entry points to `scripts/test-routes.mjs` and `scripts/test-core-views.mjs`. It preserves the strict exclusion of private project admission, audit and workflow files.
